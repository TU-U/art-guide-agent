# 项目实践报告

## 一、项目实践内容

### 1. 项目背景与意义、需求分析与项目内容

本项目围绕“具备语音交互、记忆能力和视觉理解能力的机器人问答系统”展开。随着大语言模型和多模态模型的发展，机器人不再只是执行固定指令，而是可以通过自然语言与用户交流，并结合环境图像理解现实场景。本项目的目标是在现有机器人平台上搭建一套可运行的语音交互系统，使机器人能够听懂用户问题、调用大模型生成回答，并通过语音播报反馈给用户。

项目初期曾考虑展厅导览场景，但在实践过程中发现，展厅场景对展品知识库、讲解内容和固定环境依赖较强，不利于快速验证机器人通用交互能力。因此后期将测试重点调整为日常或实验室场景，使用杯子、鼠标、键盘、箱子、外套等日常物品，重点验证语音问答、图文问答、上下文连续性和纠错记忆等能力。

项目核心需求包括：语音输入转文本、文本或图文问题理解、大模型生成回复、TTS 语音合成、长期记忆存储与召回、前端调试展示，以及后续接入视觉指向识别能力。

### 2. 项目相关概念与技术

本项目涉及 ASR、LLM、VLM、TTS、RAG 和机器人系统集成等技术。ASR 用于将用户语音转为文本；LLM/VLM 用于生成自然语言回答，其中 VLM 能够同时处理图片和文本；TTS 用于将模型回复转为语音播放。项目中选择讯飞 API 作为 TTS 方案，主要考虑其声音效果较好、接口成熟、接入成本较低 [1]。大模型方面，机器人主链路逐步切换到 Qwen Omni，用于支持纯文本与图文交互 [2]。

记忆模块采用短期对话历史和长期记忆结合的方式。短期记忆用于保存当前会话上下文，长期记忆用于记录用户传授的新知识、纠错信息和视觉摘要。例如用户纠正“箱子里的不是背包，是外套”后，系统应将该事实写入记忆，并在后续问答中召回。视觉方面，系统预留了摄像头图片、目标检测和 VLM 图文问答接口，使机器人能够围绕用户指向的现实物品回答问题。

后期重新设计项目架构时，相关论文和开源项目主要不是作为“功能照搬”的依据，而是用于判断技术路线和模块边界。ROS-LLM 和 RobotecAI RAI 对本项目的启发主要在机器人系统组织方式上：机器人不应把语音、模型、记忆、视觉和执行逻辑全部写在一个脚本里，而应围绕 ROS 节点、服务模块和状态反馈进行拆分，使每个模块能够独立启动、替换和调试 [4][8]。因此，本项目后期将机器人链路整理为 ASR、RobotBrain、VLM/LLM、Memory、TTS 和 Frontend 等模块，并通过 ROS Topic、文件状态和 HTTP 接口连接。

低延迟 Pepper 机器人多模态交互相关工作主要影响了本项目对响应速度的关注 [5]。机器人语音交互和普通网页问答不同，用户更敏感的是“多久开口”，而不是完整回答最终多久生成。因此项目后期增加了首音延迟分段日志，把记忆写入、记忆召回、模型生成、切句、TTS 合成和音频发布拆开计时；同时采用短句切分、TTS 单线程队列、TTS 预热和关闭无关展品 RAG 等方式降低等待时间。

Home Assistant LLM Vision、Qwen2.5-VL 和 InternVL 主要作为视觉问答技术路线参考 [9][10][11]。这些项目说明视觉输入可以不必一开始就做复杂动作控制，而是先作为“环境理解能力”接入问答系统。因此本项目没有直接从视觉走到机器人动作执行，而是先实现图片快照、图文问答、红框指向提示、视觉摘要和前端可视化调试，先验证机器人能否围绕现实物体进行自然对话。

YOLOv8、GroundingDINO 和 Grounded-Segment-Anything 则影响了后续视觉定位能力的预留设计 [12][13][14]。当前阶段主要使用固定目录中的最新图片和红色方框提示，后续如果目标检测或开放词汇检测稳定输出 `target_class`、`bbox`、`confidence` 等结构化结果，就可以把这些信息和图片一起传给 VLM，提高“用户指的是哪个物体”的判断准确性。

OpenVLA 和 StreamVLN 主要帮助明确了本项目当前不做什么 [6][7]。OpenVLA 更偏向视觉-语言-动作控制，StreamVLN 更关注连续视觉流导航，这些方向都比当前实习阶段的目标更复杂。因此项目最终把阶段目标收敛为“语音 + 图片 + 问答 + 记忆 + 前端调试”的轻量多模态交互系统，暂时不把动作控制、导航和端到端 VLA 作为主要实现内容。

### 3. 项目系统与功能设计

#### 3.1 系统总体架构设计

系统整体采用分层和模块化设计，将语音采集、文本识别、视觉输入、机器人主控、多模态模型调用、记忆管理、语音合成和前端调试拆分为相对独立的模块。系统将“输入、理解、记忆、生成、输出、调试”分成多个层次，每个模块只负责一类任务，再通过 ROS Topic、文件路径、函数调用和 HTTP 接口进行连接。

从整体架构看，系统可以分为七个核心部分。

第一是语音输入模块，由 `voice_to_text.py` 负责，将用户语音转换为文本，并发布到机器人主链路能够监听的位置。

第二是视觉输入模块，负责保存当前相机画面或指向识别结果，例如将最新图片保存到固定目录，供主程序在每一轮对话时读取。

第三是机器人主处理模块，由 `local_model_processor.py` 承担，它是整个系统的中枢，负责接收用户文本、判断图片是否可用、组织短期上下文和长期记忆、调用模型服务、切分模型回复、触发 TTS 生成和播放。

第四是模型服务模块，主要由 `vlm_service.py` 封装，用于调用 Qwen Omni 处理纯文本或图文输入。

第五是记忆模块，位于 `memory` 目录下，负责管理短期对话、长期事实、事件记忆和视觉摘要。

第六是语音合成模块，由 `tts_service.py` 调用讯飞 API，将模型回复转为音频文件。

第七是前端调试模块，由 `main.py` 和 `frontend` 页面提供，用于查看机器人对话、图片快照、VLM 输入图片、视觉摘要和运行日志。

系统实际运行时并不是简单地“输入一句话，调用一次模型”。主链路需要先判断当前输入是否重复、是否来自上一轮 TTS 回声、是否有可用图片、是否需要调用图文模型、是否需要写入用户纠正、是否需要召回历史记忆，然后才组织最终传给模型的上下文。这种设计可以让机器人在没有视觉输入时保持普通语音对话，在有视觉输入时自动切换为图文问答，同时保证 TTS 输出不会被多轮回复抢占。

#### 3.2 单轮交互流程设计

在功能设计上，系统围绕“每一轮用户输入”组织流程。用户说话后，ASR 模块先将语音转换成文本，并将文本传入机器人主处理程序。主程序收到文本后，会记录本轮输入到达的时间，并进行基础过滤，例如过滤空文本、重复文本和可能由机器人自己刚播放的语音引起的回声文本。通过这些处理，可以减少机器人重复回答或自问自答的情况。

完成输入过滤后，系统会进入记忆处理阶段。主程序先把用户文本写入短期对话历史，再尝试从用户输入中抽取明确事实，例如“这个杯子叫 bue”“箱子里的是外套”等。如果抽取成功，这些内容会进入长期事实记忆。随后系统根据当前问题进行记忆召回，把最近对话、相关事实、事件摘要和用户画像组合成上下文。这个上下文不会直接替代用户问题，而是作为补充信息传给模型，使模型在回答时能够参考历史内容。

接着系统判断是否需要图文输入。主程序会读取视觉模块保存的最新图片，并比较图片文件的修改时间和本轮用户输入时间。如果图片存在且时间小于10s，说明这张图片大概率对应用户当前看到或指向的场景，系统就将图片和文本一起传入 VLM。如果图片不存在，或者图片明显早于本轮用户输入（大于10s），则认为这张图片已经过期，本轮只进行纯文本问答。这个时效判断非常重要，因为机器人环境中的图片可能会被覆盖或滞后，如果不加判断，模型可能会根据上一轮图片回答当前问题，导致明显错误。

模型生成回复后，系统不会等所有后处理结束才播放，而是将回复文本送入句子切分器。切分器会根据标点和最短长度（6个字符）把回答拆成若干短句，再逐句交给 TTS 队列。TTS 队列采用单线程顺序合成和播放，保证音频不会并发抢占，也避免一句话还没有播完就插入下一句。最后，系统将本轮用户问题、机器人回答、使用图片情况、模型名称和运行事件写入前端可读取的状态文件，方便调试页面展示。

#### 3.3 图文问答与指向物体设计

图文问答部分的核心目标是让机器人能够理解现实环境中的物体，而不是只回答抽象文本问题。在日常或实验室场景中，用户经常接触到日常用品，这就需要机器人也能够识别并且辨认。这类问题如果只看文本，模型无法知道“这个”“它”“那个”具体指什么、长什么样。因此系统设计为：当存在有效图片时，将用户文本和图片一起传入 VLM，由图文模型结合画面内容生成回答。

为了让图文模型更准确地理解用户指向对象，系统设计了“指向区域优先”的提示机制。视觉模块可以在图片中用红色方框标出用户指到的区域，主链路在调用 VLM 时会附加prompt：如果用户问题和图片有关，应优先识别红色方框内的内容，默认红色方框内才是用户指到的物品。这样可以使得模型注意力在需求重点上，避免模型把整张图中最显眼但并非用户目标的物体当成答案。

后续如果 YOLO 或指向检测服务稳定输出结构化结果，系统还可以进一步把目标类别、置信度、边界框坐标和图片路径一起传给模型。例如检测结果可以包含 `target_class`、`bbox`、`confidence` 和 `frame_path` 等字段。这样 VLM 不仅能看到图片，还能知道检测模块认为用户指向的候选物体是什么。该设计兼顾了传统视觉模型的定位能力和多模态大模型的语言解释能力。

同时，系统没有把视觉功能设计成强依赖模块。如果图片服务异常、图片不存在或图片过期，机器人仍然可以退回纯文本问答。这种降级机制可以保证系统在实际测试中更稳定，不会因为摄像头或检测服务问题导致整条语音交互链路不可用。

#### 3.4 RAG 与知识检索设计

项目早期保留了展品 RAG 设计，用于展厅导览类问题。RAG 的基本流程是先用 embedding 模型将用户问题转成向量，再到向量数据库中检索相关文档片段，同时结合 BM25 等关键词检索方式获取候选内容，最后把检索结果拼接进 prompt 交给大模型生成回答。这种方式适合回答“某个展品的背景是什么”“某件作品有什么特点”等依赖固定知识库的问题。

在 embedding 模型选择上，当前新链路主要使用本地 `models/qwen3-embedding`，如果本地目录不存在则按代码逻辑退回到 `Qwen/Qwen3-Embedding-0.6B`。该模型通过 `SentenceTransformer` 加载，并在查询侧使用 Qwen3 embedding 的 query prompt 进行向量化，文档侧则直接进行归一化编码。展品检索模块还可以结合 BM25 做关键词召回，并在本地存在 `models/bge-reranker-base` 时启用 reranker 重排序。项目早期旧版向量库中也保留过 `models/bge-small-zh-v1.5` 配置，对应 `data/chroma_db_local_model`，但当前机器人主链路和新记忆召回默认复用 Qwen3 embedding。

但在实际机器人测试中，项目场景逐渐从展厅转向日常或实验室环境。此时用户更多会问眼前物体、当前图片和连续对话中的内容，而不是固定展品知识。如果每一轮普通问答都触发展品 RAG，不仅会引入无关知识，还会显著增加延迟。实际日志中也发现，展品 RAG 的 embedding 查询可能造成较长等待，影响机器人开口速度。因此系统设计上将展品 RAG 从机器人主链路中剥离，默认不参与普通语音交互。

当前系统中保留 RAG 的思路，但将其定位为“可选知识检索能力”，而不是主链路默认步骤。对于机器人日常场景，优先使用短期上下文、长期记忆和 VLM 视觉输入回答问题；只有在后续明确需要接入某个固定知识库，例如学校介绍、实验室制度、设备说明或展品资料时，才应按主题显式启用对应 RAG。这样可以避免“所有问题都检索一遍”的低效设计，也让系统更符合实际应用场景。

从设计角度看，RAG 模块和记忆模块的职责也需要区分。RAG 更适合检索外部稳定资料，例如文档、展品介绍、学校资料；记忆模块更适合保存交互中产生的新信息，例如用户纠正、现场观察、刚刚讨论过的对象和用户偏好。两者都能为模型提供上下文，但来源和更新方式不同。项目后续如果继续完善，可以将 RAG 设计为按场景加载的知识插件，而不是机器人主链路中的固定步骤。

#### 3.5 记忆模块功能设计

记忆模块是本项目区别于普通单轮问答的重要部分。普通大模型接口通常只根据当前输入生成回答，而机器人在实际交互中需要记住刚才说过什么、用户纠正过什么、某个物体被命名为什么，以及某个场景中出现过什么。因此系统将记忆分为一类短期记忆和多类长期记忆。短期记忆负责当前会话连续性；长期记忆则进一步细分为事实记忆、事件记忆、见解记忆、视觉摘要记忆和用户画像/偏好记忆。

短期记忆主要保存当前会话最近若干轮用户和机器人的对话内容，用于解决轮内上下文连续问题。例如用户先问“介绍一下这个东西”，随后追问“它是干什么用的”，系统需要通过最近对话知道“它”指的是上一轮讨论的对象。短期记忆不一定永久保存所有内容，而是更关注当前会话内的连贯性。

长期记忆主要分为五类。第一类是事实记忆，主要保存用户明确传授或纠正的信息。例如用户说“我们的教室在 211”“这个杯子叫 bue”“箱子里的其实不是背包，是外套”，系统会尝试从文本中抽取结构化事实，写入事实记忆库。事实记忆通常包含 subject、predicate、object、category、content、timestamp 等字段，便于后续检索和组织上下文。对于纠错类输入，系统会特别记录“之前识别成什么不对，正确是什么”，避免后续继续犯同样错误。

第二类是事件记忆，主要记录对话中发生过的交互事件。事件记忆不是简单保存原始聊天记录，而是把对话压缩成“发生了什么”的描述，例如“用户询问了桌上杯子的用途”“用户纠正了箱子中物体的类别”“机器人围绕某张图片回答了物体识别问题”。这类记忆适合在后续回顾某次交互或恢复上下文时使用。

第三类是见解记忆，主要来自对多轮对话的异步反思。系统在每轮回答结束后，可以将最近对话交给抽取器，生成更高层次的总结或偏好判断，例如用户最近关注某类物品、用户经常追问用途、用户更喜欢简短回答等。这类记忆不一定来自一句明确的“请记住”，而是从对话行为中总结出来，适合作为后续个性化回复的参考。

第四类是视觉摘要记忆，用于记录图文交互中的画面信息。当系统使用图片回答问题时，可以并行生成一份视觉摘要，记录图片时间、主要对象、场景内容和用户问题。这样即使图片之后被覆盖，系统仍然可以保留当时的视觉观察结果。视觉摘要不直接阻塞主回复生成，而是放在后台异步执行，避免增加用户等待时间。

第五类是用户画像/偏好记忆，用于保存更稳定的用户特征或交互偏好。例如用户属于学生、老师或访客，用户更喜欢详细解释还是简短回答，用户是否经常关注物体用途或空间位置等。这类信息可以在回答风格和内容组织上发挥作用，但当前项目中仍处于初步设计和验证阶段，后续需要更多真实交互数据来判断哪些偏好值得长期保存。

在召回设计上，系统会根据当前用户问题查询相关长期记忆，同时取出最近几轮短期历史，并将这些内容组合成 `memory_context` 传给模型。长期记忆的向量化同样复用本地 Qwen3 embedding 系列，即优先加载 `models/qwen3-embedding`，其次兼容 `models/Qwen3-Embedding-0.6B`。事实记忆、事件记忆和见解记忆等长期库使用同一套 embedding 函数写入 ChromaDB，保证不同记忆库之间的向量空间一致。为了减少延迟，记忆召回中同一个 query 只进行一次 embedding 编码，再复用该向量查询不同记忆库。这样可以避免多个记忆库重复编码同一个问题，降低响应时间。

#### 3.6 前端调试与状态展示设计

前端调试功能主要服务于开发和测试。由于机器人链路涉及多个后台服务，仅靠终端日志不便于观察整体状态，因此系统设计了专门的机器人调试页面。该页面不是面向最终用户的展示页，而是面向开发者的运行监控界面，用来快速判断机器人当前是否正常接收语音、是否拿到图片、是否调用了 VLM、是否写入视觉摘要，以及 TTS 是否正常输出。

调试页面主要展示几类信息。第一类是对话文本，包括用户语音识别结果和机器人回复内容，用于确认 ASR 和模型回复是否正常。第二类是视觉状态，包括最新图片快照和实际传入 VLM 的图片，用于判断图片是否刷新、是否过期、是否真的参与了本轮问答。第三类是模型状态，包括当前使用的模型、是否使用图片、调用路径和最近更新时间。第四类是记忆状态，包括视觉摘要和长期记忆写入事件。第五类是运行日志，包括是否获取到图片、是否传入 VLM、是否完成模型回复、是否生成 TTS 音频等事件。

通过前端页面，可以把原本分散在多个终端中的信息集中显示出来。例如当机器人回答错误时，可以先看用户文本是否识别正确，再看传入 VLM 的图片是否正确，接着看运行日志中是否提示图片过期或未获取，最后再判断是模型理解问题还是输入链路问题。这样的调试方式比单纯查看后台日志更直观，也更适合现场测试。

### 4. 项目关键技术与实现

#### 4.1 机器人主链路实现

机器人实测链路的核心文件是 `local_model_processor.py`。它相当于机器人“大脑”，负责把 ASR、视觉输入、记忆模块、大模型服务、TTS 和前端状态串成一条完整链路。

1. 输入接收：机器人通过 ROS Topic `/asr/user_text` 接收 `voice_to_text.py` 发布的识别文本。回调函数 `on_input` 只做轻量处理，然后把文本交给 `process_user_text`，避免在 ROS 回调中堆积复杂逻辑。

2. 单轮互斥：`process_user_text` 开始时会使用 `_busy_lock` 判断上一轮是否还在处理。如果上一轮模型生成或 TTS 播放还没结束，新输入会被丢弃。这样可以防止多轮语音同时进入模型，造成多个回答交叉播放。

3. 去重与回声过滤：代码维护 `last_input_text`、`last_input_time`、`last_answer`、`last_answer_time`。如果短时间内收到重复 ASR 文本，或者输入内容与机器人刚刚播出的回答高度重合，系统会认为这是重复拾音或 TTS 回声，不再进入模型。

4. 主流程顺序：一轮对话的主处理顺序是“输入过滤 -> 记忆写入 -> 记忆召回 -> 图片判断 -> 模型调用 -> 回复切句 -> TTS 合成播放 -> 状态写回”。这种顺序保证了模型回答时既能拿到当前用户问题，也能参考近期对话、长期记忆和可能存在的视觉画面。

5. 工程作用：这一层的重点不是模型能力本身，而是保证真实机器人现场运行稳定。尤其是 `_busy_lock` 和回声过滤，直接解决了语音机器人常见的重复触发、自问自答和回答互相打断问题。

关键代码示例：

```python
def on_input(self, msg: String):
    user_text = (msg.data or "").strip()
    self.process_user_text(user_text, source="topic:/asr/user_text")

def process_user_text(self, user_text: str, source: str = "unknown"):
    if not self._busy_lock.acquire(blocking=False):
        logger.info("上一轮还在生成/播放，丢弃: %s", user_text)
        return
    try:
        user_text = (user_text or "").strip()
        if not user_text or self._should_ignore_input(user_text):
            return

        self.memory_hub.record_turn(self.session_id, "user", user_text)
        recall = self.memory_hub.recall(
            query=user_text,
            user_id=self.user_id,
            session_id=self.session_id,
            top_k=3,
            history_tail=8,
        )
        image_data = self._load_latest_image_bytes(user_input_time=time.time())
        # 后续继续完成模型调用、切句、TTS 和状态写回
    finally:
        self._busy_lock.release()
```

#### 4.2 文本与图文输入切换实现

系统没有让用户手动选择“文本模式”或“图文模式”，而是在每轮语音输入到达后自动判断当前是否有可用图片。

1. 图片来源：视觉服务会把最新画面保存到固定路径，例如 `point/rviz_captured_images/latest.jpg`。该文件会被持续覆盖，因此不能只根据文件名判断图片是否属于当前轮对话。

2. 图片读取：主链路调用 `_load_latest_image_bytes(user_input_time=t0)` 读取图片。这里的 `t0` 是本轮用户文本进入主流程的时间，用来和图片修改时间进行比较。

3. 过期判断：如果图片不存在，本轮直接走纯文本问答；如果图片存在但图片修改时间早于用户输入时间超过 10 秒，则认为图片过期，不传给 VLM。这个规则避免了用户问“这个是什么”时，模型实际看到的是上一轮遗留图片。

4. VLM 输入快照：当图片有效时，系统会把图片复制到 `data/runtime/last_vlm_image.jpg`。这个文件表示“本轮真正传给 VLM 的图片”，和持续刷新的 `latest.jpg` 区分开。前端可以同时显示这两张图，方便判断模型回答依据是否正确。

5. 模式切换：图片有效时，系统调用图文链路，把用户文本、图片、历史对话和记忆上下文一起传给 VLM；图片无效时，只把文本和上下文传给模型。这样既保留普通语音问答能力，也支持用户指向物体后的图文问答。

6. 实际意义：这个设计解决的是机器人现场“先有图片、后有语音”的时序问题。因为相机画面和 ASR 文本不是同一时刻产生的，必须用时间戳判断它们是否属于同一轮交互。

关键代码示例：

```python
def _load_latest_image_bytes(self, user_input_time: float) -> Optional[bytes]:
    image_path = Config.POINT_LATEST_IMAGE_PATH
    if not image_path.exists():
        self._write_runtime_state(vlm_image_path="", used_image=False)
        return None

    image_mtime = image_path.stat().st_mtime
    if image_mtime + 10.0 < user_input_time:
        self._write_runtime_state(
            latest_image_path=str(image_path),
            vlm_image_path="",
            used_image=False,
        )
        return None

    image_bytes = image_path.read_bytes()
    Config.ROBOT_VLM_IMAGE_PATH.write_bytes(image_bytes)
    os.utime(Config.ROBOT_VLM_IMAGE_PATH, (image_mtime, image_mtime))
    self._write_runtime_state(
        latest_image_path=str(image_path),
        vlm_image_path=str(Config.ROBOT_VLM_IMAGE_PATH),
        used_image=True,
    )
    return image_bytes
```

#### 4.3 Qwen Omni 多模态模型调用实现

模型调用主要由 `services/vlm_service.py` 封装，机器人版本默认使用 Qwen Omni 相关接口，模型名配置为 `qwen3-omni-flash`。

1. 接口配置：模型所需配置集中放在 `config.py` 和 `.env` 中，包括 `DASHSCOPE_API_KEY`、`QWEN_OMNI_BASE_URL`、`QWEN_OMNI_MODEL_NAME`。代码通过 OpenAI 兼容 SDK 连接 DashScope compatible-mode 接口，降低了接口适配成本。

2. 文本与图片统一封装：`VLMService` 会把用户问题、历史对话、记忆上下文和用户画像统一组织进 messages。纯文本时，`user.content` 是普通字符串；图文输入时，`user.content` 是一个列表，其中包含文本段和 `image_url` 图片段。

3. 图片编码：图片传入模型前会先转成 base64 data URL。系统会根据图片文件头判断 MIME 类型，例如 JPEG、PNG、GIF、WebP，避免图片格式写错导致接口无法解析。

4. 路由提示：`RuleRouter` 会根据问题和图片情况给出 route，例如 `text_only`、`vision_qa`、`pointed_object_qa` 等。不同 route 会影响 system prompt，使模型知道本轮是纯文本回答、图像描述，还是指向物体问答。

5. 红框指向提示：图文交互中会额外提示模型：如果用户问题与图片有关，应重点识别红色方框内的内容，默认红框区域才是用户指到的物品。这个 prompt 是为了配合视觉定位结果，减少模型把整张图中其他显眼物体当成目标。

6. 输出约束：系统 prompt 会限制回答简洁、直接、准确，并要求模型看不清时说明不确定。机器人语音播报不适合长篇解释，所以主链路还会要求回答控制在约 100 字以内，避免 TTS 播放时间过长。

7. 降级处理：如果模型接口报错、API Key 未配置或返回空内容，服务会返回“当前模型服务不可用”等错误提示，并把错误写入运行状态，方便前端和日志定位问题。

关键代码示例：

```python
def _build_messages(self, question, decision, image_data=None,
```

#### 4.4 记忆写入、召回与 Memory RAG 实现

记忆系统由 `memory/memory_hub.py` 统一封装，对外提供短期历史、长期事实、事件、见解和用户画像等能力。本项目中的记忆召回本质上也是一种 RAG，只不过检索对象不是外部文档，而是机器人交互过程中积累的记忆。

1. 短期记忆：每轮用户输入和机器人回答都会通过 `record_turn` 写入短期历史。短期历史用于维持当前会话的连续性，例如用户先问“介绍一下这个东西”，下一轮问“它是干什么用的”，模型可以通过最近对话知道“它”指的是上一轮对象。

2. 事实记忆：`observe_user_fact` 会尝试从用户文本中抽取明确事实，例如“我们的教室在 211”“这个杯子叫 bue”“箱子里的不是背包，是外套”。这些事实会进入 `LabFactArchive`，适合保存实验室场景中的物体名称、位置、纠正信息和人为定义。

3. 事件记忆：`EventArchive` 保存“发生过什么”的摘要，例如用户询问了某个物体、用户纠正了识别结果、机器人围绕某张图片进行了回答。事件记忆比原始聊天记录更精简，适合后续恢复上下文。

4. 见解记忆：`InsightArchive` 用于保存从多轮对话中总结出的见解，例如用户关注物体用途、偏好简短回答、某类问题反复出现等。这类记忆不是一句话直接传授的事实，而是从交互行为中提炼出的长期参考。

5. 用户画像：`UserGroupProfiles` 会提供用户群体和沟通偏好信息，例如普通访客、学生、教师等。模型生成回答时可以把用户画像作为风格参考。

6. 召回流程：`MemoryHub.recall` 会取出最近若干轮短期历史，并分别查询事实记忆、见解记忆、事件记忆和用户画像，然后通过 `_compose_context` 拼成 `combined_context`。主链路再把 `combined_context` 注入模型 prompt。

7. 向量化模型：长期记忆优先使用本地 `models/qwen3-embedding`，兼容 `models/Qwen3-Embedding-0.6B`。该模型通过 `SentenceTransformer` 加载，并将向量写入 ChromaDB。事实、事件和见解记忆复用同一套 embedding 函数，保证向量空间一致。

8. 性能优化：记忆召回会尽量减少同一 query 的重复 embedding 编码，避免多个记忆库重复跑 `Batches`。这对机器人开口延迟很重要，因为 embedding 检索虽然能提升上下文能力，但如果每轮都耗时过长，会直接影响语音交互体验。

9. 视觉摘要记忆：当本轮使用图片回答问题时，系统可以在后台并行生成视觉摘要，记录图片时间、主要物体、用户问题和场景内容。这样即使 `latest.jpg` 后续被覆盖，系统也能保留当时的视觉观察结果。

#### 4.5 TTS 切句、合成与顺序播放实现

语音输出由 `services/tts_service.py` 和 `local_model_processor.py` 中的 TTS 队列共同完成。选择讯飞 API 的原因是声音效果更自然，且比本地部署 TTS 模型更省开发时间。

1. TTS 服务封装：`TTSService` 内部调用讯飞 WebSocket TTS 接口，将文本合成为 mp3 文件。合成结果保存到 `data/audio_out` 目录，文件名中包含序号和时间戳，便于调试。

2. 启动预热：机器人启动后会异步调用 `_warmup_tts`，预先合成一句“你好。”，用于减少第一次正式播报时的冷启动延迟。预热文件生成后会被删除。

3. 流式切句：`StreamSentencer` 维护一个 `buffer`。模型输出文本持续进入 buffer 后，切句器根据标点和最短长度判断是否可以切出一句。第一句门槛更低，是为了让机器人尽快开口；后续句子更强调完整性，避免切得太碎。

4. 单线程合成：TTS 队列使用 `ThreadPoolExecutor(max_workers=1)`，确保同一时间只有一个句子在合成。早期并发合成会导致多个音频几乎同时生成和播放，出现重复、抢播、断句不完整等问题，因此改为单线程顺序处理。

5. 顺序编号：每个句子进入 TTS 队列时都会分配 `idx`，并在 `_pending` 字典中占位。即使某一句合成较慢，系统也不会越过它直接播放后面的句子。

6. 顺序发布：`_drain_locked` 只会发布 `_next_play_idx` 对应的音频，发布后再递增编号。最终发送到 ROS Topic `/xunfei/tts_play` 的消息格式为 `{"cmd":"append","file":"音频路径"}`。

7. 播放间隔：当前 Brain 侧没有写死每段音频之间相隔几秒，只保证按顺序发布。实际两段音频之间的间隔取决于底层播放器如何处理 `append` 队列。如果底层播放器严格排队，就会上一段播完后继续下一段；如果底层播放器没有排队机制，仍可能出现播放侧问题。

8. 工程效果：该设计把“模型生成”和“语音播放”解耦，模型只负责产出文字，切句器负责拆分，TTS 队列负责合成顺序，底层播放器负责实际播放，问题定位更加清晰。

关键代码示例：

```python
self.tts_pool = ThreadPoolExecutor(max_workers=1, thread_name_prefix="tts")
self._play_lock = threading.Lock()
self._next_play_idx = 0
self._pending: Dict[int, Optional[str]] = {}
self._enqueue_idx = 0
```

```python
def _submit_tts(self, sentence: str):
    with self._play_lock:
        idx = self._enqueue_idx
        self._enqueue_idx += 1
        self._pending[idx] = None
    self.tts_pool.submit(self._synth_and_dispatch, idx, sentence)

def _drain_locked(self):
    while self._next_play_idx in self._pending:
        audio_path = self._pending[self._next_play_idx]
        if audio_path is None:
            break
        self._pending.pop(self._next_play_idx)
        self._next_play_idx += 1
        if audio_path:
            self._publish_play(audio_path)

def _publish_play(self, audio_path: str):
    msg = String()
    msg.data = json.dumps({"cmd": "append", "file": audio_path})
    self.tts_pub.publish(msg)
```

#### 4.6 前端状态与机器人调试页实现

为了让机器人链路可观察，项目增加了前端调试页。这个页面不是普通聊天页面，而是面向机器人现场测试的状态监控页面。

1. 状态文件：`local_model_processor.py` 通过 `_write_runtime_state` 写入运行状态，包括 `session_id`、`status`、`model_provider`、`model_name`、`last_user_text`、`last_assistant_text`、`latest_image_path`、`vlm_image_path`、`visual_summary`、`robot_events` 等字段。

2. 事件日志：`_append_runtime_event` 会追加关键事件，例如“RobotBrain started”“收到 ASR 文字”“未获取到图片，本轮走纯文本 LLM”“文字和图片已传入 VLM”“模型完成”等。事件列表会保留最近若干条，避免状态文件无限增长。

3. 前端接口：`main.py` 提供接口读取状态文件和机器人对话记录，前端页面定时轮询后展示。这样用户打开浏览器即可看到机器人链路文字版交互。

4. 页面内容：robot 页面应展示 ASR 识别文本、机器人回复、最新相机画面、实际传入 VLM 的图片、图片更新时间、视觉摘要、模型调用路径和运行日志。

5. 调试价值：当机器人回答错误时，可以按顺序排查：ASR 文本是否识别正确；图片是否刷新；传给 VLM 的是否是当前图片；是否走了图文链路；模型是否报错；TTS 是否生成。这样比只看终端日志更直观。

6. 两条链路区分：前端主页面更适合测试接口和模型能力；robot 页面对应真实机器人链路，展示 `start_all.sh` 启动后的 ASR、RobotBrain、VLM、TTS 和视觉状态。

关键代码示例：

```python
def _write_runtime_state(self, **updates):
    with self._state_lock:
        self._runtime_state.update(updates)
        self._runtime_state["updated_at"] = _now_iso()
        Config.ROBOT_BRAIN_STATE_PATH.write_text(
            json.dumps(self._runtime_state, ensure_ascii=False, indent=2),
            encoding="utf-8",
        )

def _append_runtime_event(self, message: str, level: str = "info"):
    with self._state_lock:
        events = list(self._runtime_state.get("robot_events", []) or [])
        events.append({"time": _now_iso(), "level": level, "message": message})
        self._runtime_state["robot_events"] = events[-60:]
        self._runtime_state["updated_at"] = _now_iso()
```

#### 4.7 延迟监控与链路优化实现

机器人语音交互对延迟非常敏感，因此系统在主链路中加入了分段计时日志，用数据定位慢点，而不是凭感觉优化。

1. 计时点设计：每轮输入记录 `t0` 到 `t6`。其中 `t0` 是入口时间，`t1` 是记忆写入完成，`t2` 是记忆召回完成，`t3` 是模型完成或首 token 到达，`t4` 是首句切出，`t5` 是首句 TTS 合成完成，`t6` 是音频发布到播放 Topic。

2. 分段含义：`t1-t0` 反映记忆写入耗时；`t2-t1` 反映记忆召回耗时；`t3-t2` 反映模型接口耗时；`t4-t3` 反映切句等待；`t5-t4` 反映 TTS 首句合成耗时；`t6-t0` 反映端到端开口延迟。

3. 日志输出：系统会输出“记忆写入、记忆召回、模型生成、切首句、TTS首句合成、端到端开口”等汇总信息，并对明显超标阶段做标记。这样可以快速判断是 embedding 慢、模型慢，还是 TTS 慢。

4. embedding 延迟定位：日志中如果出现 `Batches: 100%` 且耗时较长，通常说明正在执行 embedding 编码或向量召回。项目中曾发现普通问答触发展品 RAG 会导致额外等待，因此后续把展品 RAG 从机器人主链路剥离。

5. 模型延迟定位：如果记忆召回很快但 `t3` 很晚，主要瓶颈通常在 Qwen Omni/LLM 接口响应。此时应优先检查网络、API 响应时间、模型选择和 prompt 长度。

6. TTS 延迟定位：如果模型已经完成但首音仍然慢，就需要检查讯飞 TTS 合成时间、网络连接、音频文件写入和底层播放器响应。

7. 优化策略：当前主链路的优化思路是减少无关检索、限制回复长度、第一句尽早切出、TTS 预热、单线程顺序播放，并把视觉摘要等非阻塞任务放到后台线程执行。

8. 实际作用：通过这些日志，系统可以把“机器人反应慢”拆解成可定位的问题，而不是笼统地归因于模型慢。这对后续继续优化端到端语音体验很关键。

关键代码示例：

```python
t0 = time.time()
timing["t0"] = t0

self.memory_hub.record_turn(self.session_id, "user", user_text)
t1 = time.time()
timing["t1"] = t1
logger.info("记忆写入: %.3fs", t1 - t0)

recall = self.memory_hub.recall(query=user_text, session_id=self.session_id)
t2 = time.time()
timing["t2"] = t2
logger.info("记忆召回: %.3fs", t2 - t1)

# 模型完成、首句切出、TTS 合成和播放发布继续写入 t3-t6
logger.info(
    "同步段汇总: 写入=%.3fs 召回=%.3fs 模型=%s",
    timing["t1"] - timing["t0"],
    timing["t2"] - timing["t1"],
    f"{timing.get('t3', time.time()) - timing['t2']:.3f}s",
)
```

### 5. 项目部署与测试

项目部署在 Ubuntu 机器人板卡上，主要通过 `start_all.sh` 启动完整链路，包括音频驱动、ASR 服务、前端后端、视觉相关服务和机器人主处理器。部署过程中重点处理了虚拟环境路径迁移、Python 依赖缺失、Linux shell 脚本兼容性、模型目录和数据目录路径等问题。由于项目涉及 ROS2 话题通信和相机、语音等外部服务，部署和调试时也参考了 ROS2 的节点、话题和启动文件组织方式 [15]。

测试分为语音交互测试、TTS 播放测试、记忆测试、图文输入测试和前端展示测试。语音交互测试验证用户语音能否正常转文本并生成回复；TTS 测试关注音频是否完整、是否重复、是否抢播；记忆测试验证用户纠错是否能被长期保存；图文测试验证图片是否能正确传入 VLM；前端测试用于观察实时对话、图片快照和日志。当前系统已能完成基础语音问答和部分图文链路验证，但视觉模块和真实场景适配仍需继续优化。

在速度测试中，系统通过分段日志记录记忆写入、记忆召回、模型生成、切句、TTS 合成和音频播放等阶段。通过这种方式可以定位延迟来源，并判断是模型接口、embedding、TTS 合成还是播放链路导致等待时间过长。后续优化也将继续以日志数据为依据，而不是凭主观感觉调整。

## 二、总结与感悟

通过本项目实践，我对大模型机器人系统的理解从“调用一个模型接口”逐渐转向“搭建一条能在真实设备上稳定运行的交互链路”。一开始我更关注模型能不能回答问题，后来发现真正影响体验的往往不是单个模型能力，而是 ASR 是否稳定、图片是否对应当前问题、记忆是否正确召回、TTS 是否会抢播、虚拟环境是否可迁移、前端是否能看清链路状态等工程问题。机器人系统不是一个孤立的问答接口，而是语音、视觉、记忆、模型、播放和调试工具共同组成的系统。

实践过程中，我体会最深的是技术路线需要服务于阶段目标。项目早期曾考虑展厅导览和展品 RAG，但在实际测试中发现，固定展品知识库会增加链路复杂度，也容易影响机器人开口速度。后续将场景调整为日常或实验室环境后，系统目标更加清晰：先让机器人能够围绕眼前物体进行自然对话，能够结合图片回答问题，能够记住用户纠正的信息，再逐步扩展视觉定位和长期记忆能力。TTS 方案最终选择讯飞 API 也是同样的原因，它不是最复杂的方案，但在声音效果、稳定性和接入成本之间更适合当前项目。

调试过程中，我也认识到可观测性的重要性。机器人回答错误时，不能简单归因于“大模型不行”。问题可能出在 ASR 文本识别错误、图片没有刷新、传给 VLM 的不是当前图片、prompt 没有生效、记忆召回了无关内容，或者 TTS 播放产生了回声。通过前端 robot 调试页和 t0-t6 分段日志，可以把问题拆解到具体环节，这比只看终端输出更有效。尤其是首音延迟统计让我意识到，机器人交互不是只看最终答案质量，还要关注用户等待第一句话的时间。

这次实践也让我对 prompt 和架构边界有了更具体的认识。prompt 不只是几句提示词，而是系统行为约束的一部分。机器人是否记得自己是“波普”、图文问答是否关注红框、视觉摘要是否足够客观，都会受到 prompt 设计影响。因此后期将系统人设、图文交互、视觉记忆和记忆抽取拆成独立 prompt 文件，方便维护和统一前端链路与机器人链路的行为。同时，代码结构也需要避免同一逻辑在不同链路中各写一套，否则很容易出现前端正常、机器人异常的问题。

总体来说，本项目让我更真实地接触到了大模型落地到机器人场景时的复杂性。客观地说，项目里的每个模块目前都做得还比较浅：ASR、VLM、记忆、TTS、前端调试和视觉指向都还只是初步打通，距离成熟系统还有不少差距。但是它的价值在于把之前学到和调研到的技术真正串进了一条可运行链路中，也算是一次学以致用的过程。后续如果继续完善，我会优先优化三点：第一是提高图文输入的稳定性，让图片、红框和用户语音更准确地对应同一轮交互；第二是继续降低端到端延迟，减少无关检索和长回答带来的等待；第三是完善长期记忆和纠错学习，让机器人不仅能回答当前问题，也能逐渐记住用户教给它的新知识。相比完成一个演示页面，我认为这个项目更重要的收获是学会了如何把模型能力放进真实链路中，并通过工程手段让它变得可运行、可观察、可迭代。
